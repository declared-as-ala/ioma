### Sprint 4 bugs found and fixed

26. **`ProductRange.slug` typed as a string-literal union (`ProductRangeKey`) without an explicit `@Prop({ type: String })`** — the exact same root cause as bug #6 (TypeScript emits no usable `design:type` reflection metadata for a union type), but this specific instance only broke under `ts-jest`'s full `NestFactory` bootstrap in the e2e suite (`Cannot determine a type for the "ProductRange.slug" field`) — the live `nest start --watch` dev server and every manual seed/curl check throughout this sprint's build never hit it, so it went unnoticed until `pnpm test:e2e` was actually run at the end. Every other union-typed field written this sprint correctly had the explicit `type:` (established convention from bug #6); this one field was missed. Fixed by adding it; re-ran the full 7-test auth e2e suite to confirm.
27. **`nanoid` v5 is ESM-only**, and Jest's default `transformIgnorePatterns` skips all of `node_modules` — any spec importing a service that pulls in `nanoid` (`orders.service.ts`, `payments.service.ts` via `payment-provider` chain) failed with `Cannot use import statement outside a module`. The first fix attempt, `transformIgnorePatterns: ["node_modules/(?!(nanoid)/)"]`, still failed: pnpm's nested `node_modules/.pnpm/nanoid@.../node_modules/nanoid/` layout means the _first_ `node_modules/` segment is followed by `.pnpm/`, not `nanoid/`, so the negative lookahead never matches. Fixed with a pnpm-aware pattern, `node_modules/(?!.*nanoid)`, applied to both `jest.config.js` and `test/jest-e2e.json` (two separate configs, both needed the fix). Confirmed by getting from 0 passing to 14/14 unit tests and 7/7 e2e tests, not just a clean compile.
28. **Real, ship-blocking, found only by an actual Playwright browser run against the rebuilt Docker stack**: the shop page (`/shop`) rendered "No products match these filters yet." even though `curl`ing `GET /api/products` directly against the same container returned all 14 seeded products correctly. Root cause: `NEXT_PUBLIC_API_URL` was never declared as a Docker build `ARG` in `web.Dockerfile` — it was only set under `docker-compose.yml`'s `web` service `environment:` block, which affects the already-built container's _runtime_ process, not the `next build` step where Next.js inlines `NEXT_PUBLIC_*` vars into the client JS bundle. The browser's bundled `apiFetch` silently fell back to same-origin (`""`), requesting `/api/products` from the Next.js server on :3000 (which has no such route) instead of the API on :4000 — this failed silently into the same "no products" UI state as a genuinely empty catalog, so a curl-only check would never have caught it. `ENVIRONMENT.md` had already documented the "baked in at build time" rule correctly; the Dockerfile/compose wiring simply never followed its own documentation. Fixed: `web.Dockerfile` now declares `ARG NEXT_PUBLIC_API_URL=""` before the build step, `docker-compose.yml`'s dev-stack `web` service passes it via `build.args` (since the dev stack has no reverse proxy in front of `web`/`api`, unlike documented production). See `DECISIONS.md`. Verified with a real Playwright browser session completing the full guest-checkout flow against the rebuilt container, not a status-code check.
29. **AI image generation kept hallucinating fake label text onto "unbranded" product bottle photography** despite explicit "no text, no logo, no label" instructions — the first full batch of 7 generated product images all carried garbled fake brand names/copy (e.g. "VREQONE", "CYONOD", "CARLE ЗURIJE") baked into the image, which would have shipped as something readable as counterfeit branding, a direct `CLAUDE.md` violation. Not fixable by asking more forcefully within the same prompt framing (a second, stronger "no label" attempt still produced text on 2 of 7). What worked: reframing the subject as an "empty transparent glass cosmetic bottle" — i.e., describing a product state where a label would be physically implausible — rather than a "product photograph" (which the model apparently treats as inherently needing a label). Required 3 regeneration rounds; every one of the final 7 images was manually reviewed for legible text before being committed to `apps/web/public/images/products/`.
30. **Reported live by the operator**: the shop page showed no products in a real browser, even after bug #28's fix — "CORS" was the correct diagnosis on first guess. `apps/api/src/main.ts`'s `app.enableCors({ origin: process.env.APP_URL })` only ever allowed the exact string `http://localhost:3000`; opening the dev site via `http://127.0.0.1:3000` instead (the same server — browsers still treat these as different origins for CORS) got back a response with `Access-Control-Allow-Origin: http://localhost:3000`, which doesn't match the requesting origin, so the browser silently discarded every API response. This is invisible to `curl` (no CORS enforcement outside a real browser) and was invisible to the existing Playwright suite too, since `playwright.config.ts`'s `baseURL` is hardcoded to `http://localhost:3000` — every automated check in this project happened to use the one hostname that already worked. Fixed with an `allowedOrigins()` helper in `main.ts` that, only when `APP_URL`'s hostname is `localhost` or `127.0.0.1` (never for a real production domain), returns both interchangeable local forms. Verified live: `curl -X OPTIONS` with each `Origin` header now gets back a matching `Access-Control-Allow-Origin`, and a real Playwright browser session against `http://127.0.0.1:3000/en/shop` renders all 14 products with zero console errors.

### Sprint 4.6/5 verification bugs found and fixed

33. **Dual bug found while re-verifying Sprint 4.6 across all three locales**: (1) `motion-and-overlays.spec.ts` located the search trigger, cart trigger, and language-switcher trigger with hardcoded English regexes (`getByRole("button", {name: /search/i})`, `/bag/i`, `getByRole("combobox", {name: /language/i})`). These correctly never matched in `fr`/`ar`, since those elements' `aria-label`s are correctly translated ("Rechercher"/"Panier"/"Choisir la langue") — a locale-fragile test, not an app defect. (2) Tracing it surfaced a real, separate `CLAUDE.md` i18n-completeness violation in `search-drawer.tsx`: the placeholder, "Close search" aria-label, "Popular Concerns" label, the 5 concern-pill labels, and the "Go" button text were all hardcoded English literals that would have shipped untranslated in `fr`/`ar`. 34. **Reproducible, non-flaky `page.goto` "load"-event timeout on the homepage only (`/en`, `/fr`, `/ar`), traced to a self-inflicted poisoned image-optimization cache lock in the long-running dev/Docker Next.js server — not an application defect.** During the same verification pass, every test navigating to the root locale route started timing out after 60s (`waiting until "load"`), while every other route continued to pass. `curl` confirmed the raw HTTP response was fast (~0.3s) on both the homepage and a passing route, ruling out a server hang; a standalone Playwright script isolated the one subresource that never resolved: `_next/image?url=%2Fimages%2Fhomepage%2Fhero-portrait.png&w=1920&q=75`, the browser's real `srcset` request for the hero image, converting to WebP. A fresh, never-before-requested width on the _same_ source file converted correctly in under a second, proving the file itself was fine — the exact `(url, width, quality)` cache key the browser requests had been left permanently wedged, almost certainly because an earlier diagnostic script's own request to that identical key was abandoned mid-flight (browser closed while Next's dev-mode image optimizer was still resizing it), leaving Next's internal in-memory optimization-cache promise for that key never resolved or rejected. Confirmed by restarting the `web` container (`docker restart ioma-dev-web-1`): the same key now resolves in ~1.7s, and every previously-failing route (94/94 tests across `motion-and-overlays`, `public-smoke`, `bottom-tab-bar`, `guest-checkout`, `design-system.a11y`, `account-navigation`) passed cleanly on the next run. Noted here as a real, if environment-specific, failure mode worth knowing about: an aborted/timed-out manual request against Next's dev image optimizer can wedge that exact resized-image variant for every subsequent request until the server restarts.

37. **Real bug in `env.validation.ts` predating this sprint, only triggered once the API itself (not just the standalone `minio-init.ts` bucket script) first opened a MinIO connection**: `MINIO_USE_SSL: z.coerce.boolean().default(false)` — Zod's `.coerce.boolean()` is just JS `Boolean(value)`, and `Boolean("false")` is `true` (any non-empty string is truthy). `.env`'s `MINIO_USE_SSL=false` was silently coerced to `true`, so the MinIO client attempted a TLS handshake against the dev stack's plaintext endpoint (`SSL routines:tls_get_more_records: packet length too long`), and every AI-analysis image upload failed with a 500. Fixed with an explicit `z.enum(["true","false"]).default("false").transform(v => v === "true")`.
38. **Circular-import DI failure**: `common/storage/storage.module.ts` defined and exported `MINIO_CLIENT` while also importing `StorageService` from `storage.service.ts`, and `storage.service.ts` imported `MINIO_CLIENT` back from `storage.module.ts` — a same-directory circular dependency. Depending on module-evaluation order this left `MINIO_CLIENT` undefined at the point `StorageService`'s constructor ran, throwing `UndefinedDependencyException` at boot. Fixed by extracting the token into its own `storage.constants.ts` so neither file imports the other.
39. **A real, reproducible, pre-existing infrastructure defect surfaced by Sprint 6's Playwright load, not caused by Sprint 6 — flagged, not fully fixed. See "Blockers" below.** Multiple pre-existing Sprint 3/4.5/4.6 tests (`motion-and-overlays.spec.ts`'s breakpoint-overflow test, `responsive-smoke.spec.ts`'s route matrix) intermittently hung on `page.goto("/en")` under concurrent Playwright load. ### Sprint 3 (round 2) bugs found and fixed

18. **Bug #12 recurred** — a stale `apps/api/tsconfig.tsbuildinfo` corrupted a fresh build a second time (`dist/main.js` missing after `nest build` reported success), this time surfacing while testing the Contact/Newsletter modules by running the API locally. Real structural fix this time (not just deleting the file again): set `"tsBuildInfoFile": "./dist/tsconfig.tsbuildinfo"` in `packages/tsconfig/nestjs.json`, so the cache lives _inside_ `dist/` and is wiped alongside it on every build — verified by building twice in a row and confirming a full `dist/` both times.
19. Tracing that bug surfaced a second, related gap: `apps/api`'s `ConfigModule.forRoot()` never set `envFilePath`, so it defaulted to looking for `.env` in the process's CWD — `apps/api/` when run via `pnpm --filter @ioma/api ...`, not the repo root where `.env` lives. This is _why_ every earlier test command in this log had every env var passed manually on the command line — the real gap was never diagnosed until now. Fixed with an explicit `envFilePath: join(__dirname, "../../../.env")` (got the relative depth wrong on the first attempt — `dist/` is 3 levels below repo root, not 2 — caught immediately by actually running the compiled server instead of trusting the fix). Verified live: `node dist/main.js` with **zero** manually-set env vars now boots and connects to Mongo.
